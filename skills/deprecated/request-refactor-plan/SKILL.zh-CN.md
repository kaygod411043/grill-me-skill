当用户想要创建重构请求时，会调用此技能。你应依次执行以下步骤。如果你认为某些步骤没有必要，可以跳过。

1. 请用户对他们想要解决的问题以及任何可能的解决思路进行长篇、详细的描述。

2. 探索仓库，验证用户的说法并了解代码库的当前状态。

3. 询问他们是否考虑过其他选择，并向他们介绍其他方案。

4. 就实现方式采访用户。要极其细致和全面。

5. 反复推敲实现的确切范围。明确计划修改什么，以及计划不修改什么。

6. 检查代码库，了解该区域的测试覆盖情况。如果测试覆盖不足，询问用户的测试计划。

7. 将实现拆分成由微小提交组成的计划。牢记 Martin Fowler 的建议：“让每一个重构步骤都尽可能小，这样你就始终能看到程序正常运行。”

8. 创建一个包含重构计划的 GitHub issue。Issue 描述使用以下模板：

<refactor-plan-template>

## 问题陈述

从开发者的视角描述其所面临的问题。

## 解决方案

从开发者的视角描述问题的解决方案。

## 提交

一份长篇、详细的实现计划。使用纯文本编写，并将实现拆分成尽可能小的提交。每次提交后，代码库都应保持可运行状态。

## 决策文档

列出已经做出的实现决策。可以包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 开发者给出的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体文件路径或代码片段。它们可能很快就会过时。

## 测试决策

列出已经做出的测试决策。包括：

- 描述什么才是好的测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似类型的测试）

## 范围之外

描述本次重构范围之外的事项。

## 补充说明（可选）

有关本次重构的任何补充说明。

</refactor-plan-template>
