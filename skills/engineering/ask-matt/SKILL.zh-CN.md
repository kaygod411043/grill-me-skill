# Ask Matt

你不可能记住每一项技能，所以直接问。

**流程**是贯穿多项技能的一条路径。大多数路径沿着一条**主流程**前进，并有两个**入口**汇入其中。其他技能要么独立运行，要么作为底层词汇层发挥作用。

## 主流程：从想法到交付

大多数工作都会沿着这条路线推进。你有一个想法，并希望将它构建出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。当你**已有代码库**时从这里开始：它是有状态的，会将了解到的内容保存在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me`，见“独立技能”。二者都运行同一个 `/grilling` 原语；`grill-with-docs` 的不同之处在于它会留下书面记录。）
2. **分支——你能否在对话中解决所有问题？** 如果某个问题需要通过可运行的结果来回答（状态、业务逻辑，或必须亲眼看到的 UI），就绕道原型，并在两个方向上都通过 **`/handoff`** 衔接（见“跨会话”）：
   - 先用 **`/handoff`** 导出，然后基于该文件开启一个新会话，
   - 使用 **`/prototype`**，通过一次性代码回答问题，
   - 再用 **`/handoff`** 带回所学内容，并在原始想法任务中引用它。
3. **分支——这是否是一个需要多个会话的构建任务？**
   - **是** → 使用 **`/to-spec`**（将任务转换为 spec），然后通过 **`/to-tickets`** 将其拆分为 tracer-bullet ticket，每个 ticket 都声明自己的**阻塞边**。对于本地 tracker，每个 ticket 是 `.scratch/<feature>/issues/` 下的一个文件，由人工按阻塞项优先的顺序处理；对于真实 tracker，这些边会变成原生阻塞链接，因此只要阻塞项已经完成，任何 ticket 都可以被领取——为每个 ticket 启动一次 **`/implement`**，并且**每个 ticket 之间都要清除上下文**。
   - **否** → 就在当前上下文窗口中直接使用 **`/implement`**。

   无论哪种方式，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个 issue——每次完成一个红-绿切片——然后在提交前运行 **`/code-review`**，从标准（Standards）和规格（Spec）两个轴审查 diff 并收尾。如果你只想在没有完整 spec 的情况下以测试优先方式构建一个具体行为，可以单独使用 **`/tdd`**；只要想基于一个固定点审查 branch 或 PR，也可以单独使用 **`/code-review`**。

### 上下文卫生

让步骤 1 至 3 保持在**同一个不间断的上下文窗口**中——在 `/to-tickets` 完成之前不要 compact 或 clear——这样追问、spec 和 ticket 都建立在同一套思考之上。之后，每个 `/implement` 都从全新的上下文开始，并基于 ticket 工作。

限制因素是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口范围（最先进的模型约为 120k token）。如果会话在到达 `/to-tickets` 前已接近这个范围，不要在能力下降的状态下硬撑，使用 `/handoff` 并在新任务中继续。

## 入口

入口指一种会产生工作、随后汇入主流程的起始情况。

- **Bug 和请求不断堆积** → 使用 **`/triage`**。它让 issue 在不同 triage role 之间流转，并产出可供代理处理的 issue，之后由 **`/implement`** 接手。

  Triage 只适用于**并非由你创建**的 issue——bug 报告、收到的功能请求，以及任何未经整理就到来的内容。由 `/to-tickets` 生成的 ticket 已经可以交给代理处理，因此**不要对它们进行 triage**。

- **某些东西坏了** → 使用 **`/diagnosing-bugs`**。它适合棘手的问题：第一眼无法解决的 bug、间歇性 flake，或悄悄出现在两个已知正常状态之间的 regression。在建立**紧密反馈循环**之前，它拒绝进行理论推演——也就是先找到一条能针对*这个* bug 立即变红的命令——然后通过 regression test 完成修复。如果复盘发现真正的问题是缺少一个能锁定 bug 的良好 seam，它会将工作交给 **`/improve-codebase-architecture`**。

- **一项庞大而模糊的工作——绿地项目或大型功能构建，大到无法在一个会话内完成** → 使用 **`/wayfinder`**，这是这里认知要求最高的流程。当从当前位置通往目标的道路仍不可见时，它会在 issue tracker 上绘制一张由**决策 ticket** 组成的**共享地图**，并逐个解决——产出的是**决策，而不是交付物**——直到迷雾消退、路径清晰。**`/grill-with-docs`** 用来打磨你能在一个会话中把握的想法，而 wayfinder 用来处理你无法在一个会话中把握的想法；它更慢、密度也更高，因此只在这种情况下使用，绝不要用在范围明确的功能上。

  地图清晰后，**它会交接，而不是构建**：在 **`/to-spec`** 处汇入主流程，将地图中相互链接的决策压缩成可构建的计划，然后照常执行 `/to-tickets` 和 `/implement`。如果直接让地图进入 `/implement`，就会跳过这次压缩并丢掉相互链接的细节；只有当这项工作最终确实很小时，才直接进入 `/implement`。

## 代码库健康

这不是功能开发，而是维护工作。

- **`/improve-codebase-architecture`** — 只要有空闲时间，就运行它，让代码库保持适合代理工作的良好状态。它会揭示**深化机会**；选择其中一个，就会*生成一个想法*，你可以从 `/grill-with-docs` 将它带入主流程。它负责勘察并找出候选项；**`/codebase-design`**（见下文）则是设计所选方案的工作台。

## 底层词汇

两个由模型调用的参考技能运行在其他技能的*底层*，各自是其词汇的唯一事实来源。当问题出在**词语**而不是流程上时，可以直接调用它们；也可以让上面的技能自行引入它们。

- **`/domain-modeling`** — 打磨项目的*领域*语言：挑战模糊术语，解决含义过载的词（例如让“account”承担三种职责），并将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 用来让 `CONTEXT.md` 保持为清晰词汇表的主动实践。
- **`/codebase-design`** — 用于设计模块*形态*的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：在清晰的 seam 上，用小接口隐藏大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 跨会话

- **`/handoff`** — 当任务上下文已满，或需要分支出去（例如进入 `/prototype` 会话）时，它会将对话压缩到一个 Markdown 文件中。不要在原地继续，而要**开启一个新会话并引用该文件**，从而跨上下文窗口携带上下文。它是两个方向上的上下文窗口桥梁。当你需要一个**全新会话**，但又要**保留当前对话**时使用它。
- **`/compact`**（内置）— 留在**同一个对话**中，让之前的轮次被总结。在**不同阶段之间有意设置的间隔**使用它，此时你不介意丢失逐字历史。不要在阶段中途 compact，代理可能会迷失方向。`/handoff` 会分叉；`/compact` 会继续。

## 独立技能

这些技能完全位于主流程之外。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的无情访谈，但用于**没有代码库**的情况。它是无状态的：不会在本地保存任何内容，也不会构建 `CONTEXT.md`。用它来打磨任何不属于仓库的计划或设计。
- **`/prototype`** — 一个小型的一次性程序，用来回答一个设计问题：这个状态模型感觉对不对，或者这个 UI 应该是什么样子。从第一天起就把它当作一次性代码——保留答案，删除代码。它是主流程步骤 2 中的绕行路线，但只要某个设计问题很难在纸面上解决，随时都可以使用它。
- **`/research`** — 将阅读工作委派给一个**后台代理**：它根据**一手来源**调查问题，然后在仓库中留下一个带引用的 Markdown 文件。它阅读时你可以继续工作。它产出的文件应被带入 `/grill-with-docs` 的主流程——research 为思考提供材料，而不是取代思考。
- **`/teach`** — 使用当前目录作为有状态工作区，跨多个会话学习一个概念。
- **`/writing-great-skills`** — 关于如何出色编写和编辑技能的参考。

## 前置条件

**`/setup-matt-pocock-skills`** — 在第一次运行 engineering 流程前执行，用来配置其他技能所依赖的 issue tracker、triage label 和文档布局。也支持自定义 issue tracker。
