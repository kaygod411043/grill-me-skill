一个宽泛的想法出现了：它太大，单个代理会话装不下，而且笼罩在迷雾中；从当前状态通往**目的地**的道路还不可见。Wayfinding 的目标是找到这条路，而不是直接冲向目的地。本技能在仓库的 Issue 跟踪器上将道路绘制成一张**共享地图**，然后逐一处理其中的**决策任务单**。这些问题的解决结果是决策，而不是等待执行的构建切片；持续处理，直到路线清晰。

每项工作的目的地不同，而说出目的地就是绘图的第一步，因为它塑造每张任务单。目的地可能是一份准备交接和迭代的规格说明、一项规划开始前必须锁定的决策，或一项就地完成的改动，例如数据结构迁移。地图不限定领域，工程工作、课程内容或其他符合这种形态的工作都可以使用。

## 规划，不要执行

Wayfinder 默认用于**规划**：每张任务单解决一项决策；当道路已经清晰，执行者动手前不再有任何待决事项时，地图就完成了。想要直接开始工作的冲动通常说明你已到达地图边缘，应当交接。某项工作可以在其 **Notes** 中覆盖这一点，让地图本身包含执行；除此之外，应产出决策，而不是交付物。

## 用名称引用

每张地图和每张任务单都是 issue，因此都有一个**名称**，也就是标题。在人类用户阅读的所有内容中，包括叙述和地图的 Decisions-so-far，都要用名称引用，绝不只写 id、编号或 slug。满墙的 `#42, #43, #44` 无法阅读；名称可以一眼扫懂。id 和 URL 不会消失，名称包裹其链接；它们存在于名称_内部_，绝不能代替名称。

## 地图

地图是本仓库 Issue 跟踪器上的一个 issue，带有 `wayfinder:map` label，是规范产物。它的任务单是地图的 child issue。

地图是**索引**，不是存储。它列出已经作出的决策，并指向保存详细内容的任务单；每项决策只存在于一个位置，也就是其任务单。因此地图绝不复述决策，只给出摘要和链接。

**地图、child ticket、blocking 和 frontier 查询在物理上保存在哪里，取决于具体跟踪器。**Issue 跟踪器应该已经提供；如果没有，运行 `/setup-matt-pocock-skills`。查阅跟踪器文档中的 “Wayfinding operations” 章节，了解_此_仓库如何表达这些操作。如果没有提供跟踪器，默认使用 local-markdown 跟踪器。

### 地图正文

这是整张地图的低分辨率视图，每个会话只加载一次。未关闭的任务单**不会**列在正文中；它们是打开的 child issue，通过查询发现。

```markdown
## Destination

<到达地图终点时的样子：这项工作正在寻找的规格说明、决策或改动。用一到两行表达；每个会话在选择任务单前都以它为方向。>

## Notes

<领域；每个会话都应查阅的技能；这项工作的长期偏好>

## Decisions so far

- [<已关闭任务单标题>](link) — <答案的一行摘要>

## Not yet specified

<!-- 见 “Fog of war”：范围内但还无法写成任务单的迷雾；随前沿推进而转化为任务单 -->
```

### 任务单

每张任务单都是地图的 **child issue**；跟踪器的 issue id 就是它的身份。正文是需要解决的问题，规模应适合一个 100K token 的代理会话：

```markdown
## Question

<这张任务单要解决的决策或调查>
```

每张任务单带一个 `wayfinder:<type>` label，可以是 `research`、`prototype`、`grilling` 或 `task`（见[任务单类型](#任务单类型)）。

会话必须在开始任何工作之前，**首先**将任务单分配给驱动地图的 dev，以此**领取**它，让并发会话跳过。这位 assignee 就是领取标记：打开且未分配的任务单尚未被领取。

阻塞使用跟踪器的**原生**依赖关系。这一点至关重要，因为它会在跟踪器自己的 UI 中_可视化_前沿，让人类用户无需打开地图就能看到哪些工作可以领取。只有不支持原生 blocking 的跟踪器才回退到正文约定。当阻塞某张任务单的所有任务单都已关闭时，它就是**未阻塞**的；**前沿**是所有打开、未阻塞且无人领取的 child issue，也就是已知范围的边缘。

答案不属于正文，而是在解决时记录（见[处理地图](#处理地图)）。解决任务单时创建的产物应从 issue 链接，而不是粘贴进去。

## 任务单类型

每张任务单要么是 **HITL**，即 human in the loop，与能够代表自己发言的人类共同处理；要么是 **AFK**，由代理独立驱动。HITL 任务单只能通过实时交流解决；代理绝不能代替人类用户回答属于对方的问题（自行回答自己问题的 grilling 代理已经破坏了流程）。

- **Research**（AFK）：阅读文档、第三方 API 或知识库等本地资源，找出决策等待的事实。由 `/research` **子代理**解决。当需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：制作便宜、粗糙且具体的产物供人反应，从而提高讨论保真度，例如大纲、粗稿、stub，或通过 /prototype 技能构建 UI/logic code。将原型作为产物链接。当关键问题是“它应该看起来怎样”或“它应该如何表现”时使用。
- **Grilling**（HITL）：通过 /grilling 和 /domain-modeling 技能开展对话，每次提出一个问题。这是默认类型。
- **Task**（HITL 或 AFK）：在作出一项_决策_前必须完成的手工工作；其中没有决策、原型或研究，但讨论在完成前被阻塞。例如注册服务以判断其 API、配置访问权限、移动数据以便查看其结构。这是唯一进行_执行_而非决策的类型；它之所以存在，是因为能解除决策阻塞，而不是因为它能交付目的地。代理在可行时独立驱动（AFK），否则向人类提供精确的 checklist（HITL）。工作完成时即解决；答案记录已经做了什么，以及后续任务单依赖的事实（credential 位置、新 URL、row count）。

## 战争迷雾

地图_有意_保持不完整：不要绘制当前还看不见的内容。现有任务单之外是**战争迷雾**，你隐约知道一些决策和调查即将出现，但因为它们依赖仍然开放的问题，所以还无法明确。解决一张任务单会驱散它前方的迷雾，将现在可以明确的内容转化成新任务单；一次一张，直到通往目的地的道路清晰，并且不再剩下任务单。

地图的 **Not yet specified** 章节用于记录这种模糊视图：疑似存在的问题、以后需要重访的区域。它是朝向目的地的未发现前沿；这里的所有内容都在范围内，只是还不够清晰，无法成为任务单。根据视野允许的程度，写得宽泛或完整均可；对于想了解工作走向的协作者，它同时也是路标。

**迷雾还是任务单？**判断标准是现在能否精确陈述问题，_而不是_现在能否回答它。

- 当问题已经清晰时，创建**任务单**，即使它还被阻塞、目前无法行动。
- 当问题还无法如此清晰地表达时，放入 **Not yet specified**。不要预先将迷雾切成任务单大小；它比任务单更粗糙，一个迷雾区块在前沿到达后可能转化为几张任务单，也可能一张都没有。

**Not yet specified** 不包含已经决定的内容（Decisions so far）、已有的任务单，以及范围外内容（见下一节）。

## 范围外

迷雾只会朝_目的地_聚集。目的地确定范围，因此超出目的地的工作属于**范围外**；它不是迷雾，也不属于 **Not yet specified**。它在地图上有独立的 **Out of scope** 章节，用于记录你有意识地排除在_本次_工作之外的内容。是否放在这里取决于范围，而不是清晰度。

范围外工作绝不会转化；前沿在目的地停止。只有重新绘制目的地时，它才会重新出现，而且应作为全新工作，而不是恢复原工作。

将某项内容排除在范围外是一项划定范围的行为，不是路线上的一步。如果已经存在的任务单后来被发现位于目的地之外，无论是绘图时错误纳入，还是解决其他任务单后才暴露，都要**关闭它**（关闭的任务单明确不在前沿），并在 **Out of scope** 中留下一行：摘要、超出范围的原因，以及指向已关闭任务单的链接。它不属于 **Decisions so far**，后者记录真正走过的路线；范围边界不是路线上的一步。

## 调用方式

有两种模式。无论哪种，**每个会话都绝不能解决超过一张任务单**，research 任务单除外。

### 绘制地图

用户用一个宽泛想法调用。

1. **命名目的地。**运行一次 `/grilling` 和 `/domain-modeling` 会话，明确地图要通向什么：规格说明、决策或改动。目的地确定范围，因此必须最先敲定。
2. **绘制前沿。**再次进行深度追问，这次采用**广度优先**：横向展开整个空间，而不是在一条线索上深入；找出开放决策和当前可以采取的第一步。**如果没有发现迷雾**，说明通往目的地的道路已经清晰，整段旅程足够小，一个会话就能完成，因此不需要地图。停下来，询问用户希望如何继续。
3. **创建地图**（label `wayfinder:map`）：填写 Destination 和 Notes，Decisions-so-far 留空，将迷雾勾勒到 **Not yet specified** 中。
4. 将现在能够明确的任务单创建为地图的 child issue，然后在**第二轮**连接阻塞边（issue 必须先有 id 才能互相引用）。连接会将它们区分为前沿和阻塞项；尚无法明确的一切继续留在迷雾，也就是 **Not yet specified** 章节。
5. **启动 research 子代理。**对于刚创建的每张 `research` 任务单，启动一个 `/research` 子代理并行解决，将研究结论保存在一次性的 `research/<name>` 分支上，并从任务单添加 context pointer。
6. 停止。绘制地图是一个会话的工作，它不会亲自解决任何任务单。

### 处理地图

用户通过地图（URL 或编号）调用。任务单是**可选的**；如果用户没有指定，就由你而不是用户选择下一项决策。

1. 加载**地图**，也就是低分辨率视图，而不是每张任务单的正文。
2. 选择任务单。如果用户指定了一张，就使用它；否则按顺序选择第一张前沿任务单。**领取它**：在开始任何工作前将它分配给自己。
3. 解决它，并**按需放大**：需要时获取任何相关或已关闭任务单的完整正文；调用 `## Notes` 区块指定的技能。如有疑问，使用 `/grilling` 和 `/domain-modeling`。
4. 记录解决结果：将答案发布为**解决评论**，**关闭** issue，并向地图的 Decisions-so-far **追加 context pointer**。
5. 添加新发现的任务单（先创建再连接）；将答案变得可明确的迷雾转化为任务单，并从 **Not yet specified** 清除每个已转化区块，使它只存在于新的任务单中。如果答案显示某张任务单（当前或其他）位于目的地之外，应将它**排除在范围外**，而不是当作路线上的一步解决。如果决策使地图的其他部分失效，更新或删除相应任务单。

用户可能并行处理未阻塞的任务单，因此要预期其他会话会同时编辑跟踪器。
