# 转为任务单

将计划、规格说明或对话拆分成一组**任务单**：每张都是曳光弹式垂直切片，并声明会**阻塞**它的其他任务单。

Issue 跟踪器和分诊 label 词汇应该已经提供；如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

使用对话上下文中已有的内容。如果用户通过参数传入引用（规格说明路径、issue 编号或 URL），获取并完整读取其正文和评论。

### 2. 探索代码库（可选）

如果尚未探索代码库，先了解代码的当前状态。任务单标题和描述应使用项目领域术语表中的词汇，并遵守所触及区域中的 ADR。

寻找预重构（prefactor）代码的机会，让实现更容易。“先让改动变容易，再完成这个容易的改动。”

### 3. 起草垂直切片

将工作拆分为**曳光弹**任务单。

<vertical-slice-rules>

- 每个切片都以狭窄但完整的路径贯穿所有层（schema、API、UI、测试），必须是垂直切片，**不能**是单层的水平切片
- 完成后的每个切片都能独立演示或验证
- 每个切片的规模都能装入一个全新的 context window
- 所有预重构都应最先完成

</vertical-slice-rules>

为每张任务单指定其**阻塞边**，也就是它开始前必须完成的其他任务单。没有 blocker 的任务单可以立即开始。

**宽范围重构是垂直切片的例外。****宽范围重构**是一个机械改动，例如重命名一列或重新定义共享 symbol 的类型；它的**爆炸半径**扩散到整个代码库，一次修改就会破坏数千个调用点，任何垂直切片都无法以绿色状态落地。不要强行把它变成曳光弹，应按**扩展-收缩（expand-contract）**排序。首先扩展：在旧形式旁添加新形式，确保没有内容损坏。然后根据爆炸半径，以批次（按 package、按目录）迁移调用点；每个批次都是被扩展任务单阻塞的独立任务单，并且因为旧形式仍然存在，所以批次之间的 CI 保持绿色。最后收缩：确认没有调用方后删除旧形式，这张任务单被每个迁移批次阻塞。如果连单独的批次也无法保持绿色，仍保留该顺序，但让它们共享一个 integration branch，并全部阻塞最终的集成与验证任务单；只在最终任务单承诺绿色。

### 4. 询问用户

将建议的拆分以编号列表呈现。对每张任务单展示：

- **Title**：简短的描述性名称
- **Blocked by**：开始前必须完成的其他任务单（如有）
- **What it delivers**：这张任务单能打通的端到端行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确，也就是每张任务单是否只依赖真正会阻挡它的任务单？
- 是否应进一步合并或拆分某些任务单？

持续迭代，直到用户批准拆分方案。

### 5. 将任务单发布到已配置的跟踪器

发布已获批准的任务单。具体**方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器；任务单本身相同，只有阻塞边的表达形式不同：

- **本地文件**：在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张任务单写一个文件，从 `01` 开始按依赖顺序编号（blocker 在前）。每个文件的 “Blocked by” 列出它依赖的编号和标题。使用下方的单任务单文件模板，一张任务单一个文件，绝不合并到一个文件中。
- **真实 Issue 跟踪器（GitHub、Linear 等）**：按依赖顺序发布，每张任务单一个 issue（blocker 在前），让每条阻塞边可以引用真实标识符。如果平台提供原生 blocking / sub-issue 关系，就使用它；否则在每张任务单的 “Blocked by” 中列出阻塞 issue。除非另有指示，应用 `ready-for-agent` 分诊 label；这些任务单按构造即可由代理领取。

处理**前沿（frontier）**：所有 blocker 都已完成的任意任务单。对于纯线性链，这意味着从上到下处理。

**不要**关闭或修改任何 parent issue。
