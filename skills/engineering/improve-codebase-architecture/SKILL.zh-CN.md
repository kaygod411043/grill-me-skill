# 改进代码库架构

揭示架构摩擦，并提出**深化机会**，即把浅层模块重构为深层模块。目标是提高可测试性和 AI 可导航性。

此命令以项目的领域模型为依据，并建立在一套共享设计词汇之上：

- 运行 `/codebase-design` skill，获取架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除检验、“接口就是测试表面”、“一个适配器 = 假想接缝，两个 = 真实接缝”）。在每条建议中严格使用这些术语，不要偏移到“component”“service”“API”或“boundary”。
- `CONTEXT.md` 中的领域语言为优秀接缝命名；`docs/adr/` 中的 ADR 则记录此命令不应重新争论的决策。

## 流程

### 1. 探索

**扫描前先限定范围，遵循 YAGNI。** 深化模块的收益在于让将来的修改更容易，因此应特别关注代码库中近期发生过变更的部分。先决定*去哪里*看，再开始查看：

- 如果用户指出了方向，例如某个模块、子系统或痛点，就沿着该方向，跳过下面的推断。
- 否则，回溯足够长的一段提交历史（`git log --oneline`），寻找代码库热点，即反复出现的文件和区域，并优先让这些路径引导注意力。如果变更分散，没有明显热点，则扩大范围。

首先阅读项目的领域术语表（`CONTEXT.md`）以及与你将触及的区域有关的 ADR。

然后使用 Agent 工具并设置 `subagent_type=Explore` 遍历代码库。不要遵循僵化的启发式规则，应自然探索，并记录遇到摩擦的位置：

- 理解一个概念时，是否必须在许多小模块之间反复跳转？
- 哪些模块是**浅层的**，接口几乎与实现一样复杂？
- 哪些纯函数只是为了可测试性而被抽取，但真正的缺陷隐藏在调用方式中，缺少**局部性**？
- 哪些紧密耦合的模块越过接缝发生泄漏？
- 代码库的哪些部分未经测试，或难以通过现有接口进行测试？

对任何疑似浅层的对象应用**删除检验**：删除它会让复杂性集中，还是只会把复杂性挪到别处？你要寻找的信号是“会集中”。

### 2. 用 HTML 报告呈现候选项

把一个自包含 HTML 文件写入操作系统临时目录，确保仓库中不留下任何内容。先从 `$TMPDIR` 解析临时目录，不存在则回退到 `/tmp`（Windows 使用 `%TEMP%`）；文件路径使用 `<tmpdir>/architecture-review-<timestamp>.html`，确保每次运行都创建新文件。为用户打开文件：Linux 使用 `xdg-open <path>`，macOS 使用 `open <path>`，Windows 使用 `start <path>`；同时告知用户绝对路径。

报告通过 CDN 使用 **Tailwind** 进行布局和样式设置；当图、流程或时序能可靠地表达结构时，通过 CDN 使用 **Mermaid** 绘图。混合 Mermaid 与手工 CSS/SVG 视觉效果：关系本身呈图结构时（调用图、依赖、时序）使用 Mermaid；想要更具编辑感的效果（质量图、剖面图、折叠动画）时，使用手工 div/SVG。每个候选项都要有一组**之前/之后可视化**。要以视觉为主。

为每个候选项渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么会造成摩擦
- **解决方案**：用通俗语言说明将发生哪些变化
- **收益**：用局部性和杠杆效应解释，并说明测试将如何改善
- **之前/之后图**：并排、定制绘制，展示浅层状态和深化效果
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，以徽章呈现

报告末尾添加**首要建议**章节：说明应首先处理哪个候选项，以及原因。

**领域概念使用 CONTEXT.md 词汇，架构使用 `/codebase-design` 词汇。** 如果 `CONTEXT.md` 定义了“Order”，就说“Order intake module”，而不是“FooBarHandler”，也不是“Order service”。

**ADR 冲突**：如果某个候选项与现有 ADR 冲突，只有当摩擦真实且足以重新审视 ADR 时才呈现。在卡片中明确标注，例如警告提示：*“contradicts ADR-0007 — but worth reopening because…”*。不要列出 ADR 所禁止的每一种理论重构。

完整 HTML 脚手架、图表模式和样式指南见 [HTML-REPORT.zh-CN.md](HTML-REPORT.zh-CN.md)。

此时不要提出接口。写完文件后询问用户：“你想探索其中哪一个？”

### 3. 追问循环

用户选定候选项后，运行 `/grilling` skill，与用户一起遍历决策树：约束、依赖、深化模块的形状、接缝背后放什么、保留哪些测试。

决策逐渐明确时，应即时产生副作用：运行 `/domain-modeling` skill，在过程中保持领域模型同步：

- **用 `CONTEXT.md` 中不存在的概念为深化模块命名？** 将术语加入 `CONTEXT.md`。如果文件不存在，则惰性创建。
- **在对话中打磨了模糊术语？** 当场更新 `CONTEXT.md`。
- **用户基于具有承重作用的理由否决候选项？** 提议 ADR，表述为：*“需要我把它记录为 ADR，避免未来的架构审查再次提出这项建议吗？”* 只有当未来的探索者确实需要这个理由才能避免重复建议时才提议；跳过临时理由（“现在不值得做”）和不言自明的理由。
- **想为深化模块探索备选接口？** 运行 `/codebase-design` skill，并使用其中 design-it-twice 的并行子代理模式。
