# 原型

原型是**用于回答一个问题的一次性代码**。问题决定其形态。

## 选择分支

从用户提示、周边代码中判断要回答的问题；如果用户在线，也可以询问：

- **“这个逻辑/状态模型合理吗？”** → [LOGIC.zh-CN.md](LOGIC.zh-CN.md)。构建一个微型交互式终端应用，推动状态机经历那些很难在纸面上推理的情况。
- **“这应该是什么样子？”** → [UI.zh-CN.md](UI.zh-CN.md)。在单个路由上生成多个截然不同的 UI 变体，通过 URL 查询参数和浮动底栏切换。

两个分支会产出截然不同的制品，选错分支会浪费整个原型。如果问题确实含糊，而且无法联系用户，则默认选择更符合周边代码的分支（后端模块 → 逻辑，页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性的，并明确标注。** 把原型代码放在接近其实际使用位置的地方（紧邻正在为之创建原型的模块或页面），使上下文一目了然；但命名必须让随意浏览的读者看出它是原型，而非生产代码。对于一次性 UI 路由，遵循项目已有的路由约定，不要创造新的顶层结构。
2. **一条命令即可运行。** 使用项目现有任务运行器支持的形式，例如 `pnpm <name>`、`python <path>`、`bun <path>`。用户无需思考就能启动它。
3. **默认不持久化。** 状态保存在内存中。持久化是原型要*检验*的对象，不应成为原型的依赖。如果问题明确涉及数据库，使用临时数据库或名称清楚标注“PROTOTYPE — wipe me”的本地文件。
4. **跳过打磨。** 不写测试，不添加超出保证原型*可运行*范围的错误处理，也不做抽象。重点是快速学到东西。
5. **展示状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看清发生了什么变化。
6. **完成后留存。** 将所有经过验证的决策融入真实代码，然后把原型本身作为**第一手资料**留存：提交到 main 之外的一次性分支，并在实现 issue 中留下指向该分支的上下文链接。答案也要留存：在 issue 或 commit 中记录结论，以及它解决的问题。main 分支只保留经过验证的决策。
