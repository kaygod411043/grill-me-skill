# UI 原型

在单个路由上生成**多个截然不同的 UI 变体**，通过浮动底栏进行切换。用户在浏览器中来回切换，选中一个（或从每个变体中取一部分），然后丢弃其余部分。

如果问题涉及逻辑/状态，而不是某个东西应有的外观，则选错了分支。使用 [LOGIC.zh-CN.md](LOGIC.zh-CN.md)。

## 何时适合这种形态

- “这个页面应该是什么样子？”
- “我想在作出决定前，先看看这个仪表板的几个选项。”
- “为设置页面尝试不同的布局。”
- 任何用户原本会花一天时间在脑中三个模糊 mockup 之间犹豫的情况。

## 两种子形态：强烈优先选择子形态 A

当 UI 原型**紧贴应用的其他部分**时，更容易判断优劣：真实页头、真实侧边栏、真实数据、真实密度。单独存在的一次性路由处于真空中，每个变体孤立看起来都不错。只要有合理的现有页面可以承载变体，就默认使用子形态 A。只有原型确实无处安放时，才选择子形态 B。

### 子形态 A：调整现有页面（首选）

路由已经存在。变体在**同一路由**上渲染，由 `?variant=` URL 查询参数控制。现有数据获取、参数和身份验证全部保留，只有渲染内容切换。这是默认选择，除非有具体理由，否则就使用它。

如果要创建原型的内容还没有自己的页面，但*本来就应该放在某个页面内*（例如仪表板的新区域、设置页面的新卡片、现有流程的新步骤），仍然属于子形态 A。把变体挂载到宿主页面内部。

### 子形态 B：新页面（最后手段）

只有正在创建原型的对象确实没有现有页面可放时才使用，例如全新的顶层表面，或无法合理嵌入任何位置的流程。

按照项目已有的路由约定创建**一次性路由**，不要创造新的顶层结构。命名应明确表明它是原型，例如在路径或文件名中包含 `prototype`。使用相同的 `?variant=` 模式。

决定采用子形态 B 前，再检查一次：真的没有现有页面可嵌入吗？空路由会隐藏那些在充实页面中才会暴露的设计问题。

两种子形态使用完全相同的浮动底栏。

## 流程

### 1. 陈述问题并确定 N

默认为**3 个变体**。超过 5 个后，它们就不再是截然不同的方案，而会变成噪音；上限设为 5。

在原型所在位置或文件顶部注释中，用一行写下计划：

> “在现有 `/settings` 路由上提供设置页面的三个变体，通过 `?variant=` 切换。”

无论用户是否在线提出异议，这都有效。

### 2. 生成截然不同的变体

起草每个变体。每个变体都必须遵守：

- 页面用途及其可访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、信息层级和主要操作，而不只是不同的颜色。三个略有调整的卡片网格不是 UI 原型，只是壁纸。如果两个草稿过于相似，使用明确的“不要使用卡片网格”要求重做其中一个。

### 3. 将它们连接起来

在路由上创建单个切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：在切换器上方保留所有现有数据获取逻辑，每个变体只替换渲染子树。

对于子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

### 4. 构建浮动切换器

在屏幕底部中央放置一个小型固定定位栏，包含三部分：

- **左箭头**：循环切换到前一个变体。
- **变体标签**：显示当前变体 key；如果变体导出了名称，也一并显示，例如 `B — Sidebar layout`。
- **右箭头**：循环切换到后一个变体。

行为：

- 点击箭头更新 URL 查询参数（使用框架路由器，例如 Next 的 `router.replace`、React Router 的 `navigate`），使变体可分享，并能在重新加载后保持不变。
- 键盘：`←` 和 `→` 方向键也能切换。当焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时，不要拦截方向键。
- 与页面视觉上明显区分（例如高对比度 pill、轻微阴影），让人一眼看出它不属于正在评估的设计。
- 在生产构建中隐藏：通过 `process.env.NODE_ENV !== 'production'` 或等价检查控制，防止原型被意外合并后把切换栏发布给用户。

把切换器放在单个共享组件中，让两种子形态都能复用。将它放在项目用于共享 UI 的位置。

### 5. 交给用户

提供 URL（以及 `?variant=` key）。用户会在方便时来回切换。最有价值的反馈通常是：**“我想要 B 的页头，再配上 C 的侧边栏。”** 这才是他们真正想要的设计。

### 6. 留存答案并清理

选出获胜变体后，记录答案，即哪个变体获胜以及原因；然后按照 [SKILL](SKILL.zh-CN.md) 所述方式留存原型。把获胜方案融入真实代码，其余内容移到一次性分支，而不是 main：

- **子形态 A**：把获胜方案融入现有页面；从 main 中删除落选变体和切换器。
- **子形态 B**：把获胜变体提升为真实路由；从 main 中删除一次性路由和切换器。

完整变体集合是第一手资料，因此应放在一次性分支，而不是垃圾桶。留在 main 分支中的变体组件和切换器很快就会腐化，并让下一位读者困惑。

## 反模式

- **变体只在颜色或文案上不同。** 那是微调，不是原型。真正的变体在结构上存在分歧。
- **变体之间共享过多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 会破坏原型的意义。每个变体都应可以自由抛弃布局。
- **把变体接到真实写操作。** 只读原型没有问题。如果变体需要修改数据，让它指向 stub。问题是“这应该是什么样子”，而不是“后端能否工作”。
- **直接把原型发布到生产环境。** 变体代码是在原型约束下编写的（无测试、最小错误处理）。把它融入真实代码时，应正确重写。
