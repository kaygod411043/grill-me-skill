# ADR 格式

ADR 位于 `docs/adr/`，并按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

惰性创建 `docs/adr/` 目录，只在需要第一份 ADR 时创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

仅此而已。一份 ADR 可以只有一个段落。价值在于记录*作出了什么*决策以及*为什么*，而不是填满各个章节。

## 可选章节

仅在确实有价值时包含以下内容。大多数 ADR 都不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：适用于重新审视决策时
- **Considered Options**：仅当被否决的备选方案值得记住时
- **Consequences**：仅当需要指出不明显的下游影响时

## 编号

扫描 `docs/adr/` 中已有的最大编号，然后加一。

## 何时提议 ADR

以下三个条件必须全部满足：

1. **难以逆转**：日后改变主意的成本很高
2. **缺少上下文时令人意外**：未来读者看到代码时会疑惑“他们为什么会这样做？”
3. **真实权衡的结果**：确实存在多个可行方案，而你基于具体理由选择了其中一个

如果决策很容易逆转，就跳过它，因为之后直接反转即可。如果它并不令人意外，就不会有人疑惑原因。如果不存在真正的备选方案，那么除了“我们选择了显而易见的做法”之外，也没有什么值得记录。

### 符合条件的内容

- **架构形态。** “我们使用 monorepo。”“写模型采用 event sourcing，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过 domain events 通信，而不是同步 HTTP。”
- **会造成锁定的技术选择。** 数据库、消息总线、身份验证提供商、部署目标。不是每个库都算，只包括需要一个季度才能替换的选择。
- **边界和范围决策。** “Customer 数据由 Customer 上下文拥有，其他上下文只能通过 ID 引用。”明确的否定与肯定同样有价值。
- **有意偏离显而易见的路径。** “因为 X，我们使用手写 SQL 而不是 ORM。”任何会让理性读者预期相反做法的决策都属于此类。这能防止下一位工程师去“修复”某个刻意为之的选择。
- **代码中不可见的约束。** “由于合规要求，我们不能使用 AWS。”“由于合作方 API 合约，响应时间必须低于 200ms。”
- **否决理由并不明显的备选方案。** 如果你考虑过 GraphQL，并出于微妙原因选择 REST，就记录下来，否则六个月后还会有人再次建议 GraphQL。
