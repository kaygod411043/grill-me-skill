本技能利用当前对话上下文和对代码库的理解生成一份规格说明（你可能将这种文档称为 PRD）。**不要**访谈用户，只综合你已经知道的内容。

Issue 跟踪器和分诊 label 词汇应该已经提供；如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果尚未探索仓库，先了解代码库的当前状态。在整个规格说明中使用项目领域术语表中的词汇，并遵守所触及区域中的 ADR。

2. 勾勒用于测试该功能的接缝。优先使用现有接缝，而不是新增接缝。使用尽可能高层的接缝。如果需要新增接缝，在你能找到的最高层提出。代码库中的接缝越少越好，理想数量是一个。

与用户确认这些接缝符合他们的预期。

3. 使用以下模板编写规格说明，然后发布到项目 Issue 跟踪器。应用 `ready-for-agent` 分诊 label，无需额外分诊。

<spec-template>

## Problem Statement

从用户视角描述用户面临的问题。

## Solution

从用户视角描述问题的解决方案。

## User Stories

一份很长的编号用户故事列表。每个用户故事应采用以下格式：

1. As an <actor>, I want a <feature>, so that <benefit>

<user-story-example>
1. 作为一名手机银行客户，我希望看到各账户的余额，以便更明智地决定如何支出
</user-story-example>

这份用户故事列表必须极其全面，覆盖该功能的所有方面。

## Implementation Decisions

列出已经作出的实现决策，其中可以包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 开发者提供的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段，它们可能很快过时。

例外：如果原型生成的片段比散文更精确地编码了一项决策（状态机、reducer、schema、type shape），将它内联到相关决策中，并简要注明它来自原型。只保留承载决策的部分，不要保留可运行 demo，只保留重要内容。

## Testing Decisions

列出已经作出的测试决策，包括：

- 描述什么构成好测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似类型的测试）

## Out of Scope

描述不在本规格说明范围内的内容。

## Further Notes

关于该功能的其他说明。

</spec-template>
