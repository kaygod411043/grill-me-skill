# 测试驱动开发

TDD 是红 → 绿循环。本技能提供让这个循环产出值得保留的测试所需的参考：什么是好测试、测试应放在哪里、反模式，以及循环规则。每个章节都适用于每次循环；在循环开始前和进行中查阅，而不是结束后才看。

探索代码库时，读取 `CONTEXT.md`（如果存在），使测试名称和接口词汇与项目的领域语言一致，并遵守所触及区域中的 ADR。

## 什么是好测试

测试应通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变，测试不应随之失效。好测试读起来像规格说明，例如“user can checkout with valid cart”明确表达了现有能力；它不关心内部结构，因此能经受重构。

示例见 [tests.zh-CN.md](tests.zh-CN.md)，mock 指南见 [mocking.zh-CN.md](mocking.zh-CN.md)。

## 接缝：测试放在哪里

**接缝（seam）**是进行测试的公共边界：你在这里观察行为，而无需伸入内部。测试存在于接缝处，绝不针对内部实现。

**仅在预先约定的接缝处测试。**编写任何测试前，先写下要测试的接缝并与用户确认。不得在未确认的接缝处编写测试。你无法测试一切；提前约定接缝，才能让测试工作落在关键路径和复杂逻辑上，而不是每个边缘情况上。

询问：“公共接口是什么？我们应测试哪些接缝？”

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（例如查询数据库，而不是使用接口）。识别信号：行为没变，但重构会使测试失败。
- **同义反复**：断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、手工用同样方式生成的 snapshot、断言常量等于自身），所以测试按构造必然通过，永远无法与代码产生分歧。期望值必须来自独立的事实来源，例如已知正确的字面量、演算过的示例或规格说明。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测试的是事物的_形状_而非面向用户的行为；测试对真实变化变得不敏感；你还会在理解实现前就锁定测试结构。改用**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是一枚**曳光弹**，根据上一轮学到的内容作出响应。

## 循环规则

- **先红后绿。**先编写失败测试，再只写足以使它通过的代码。不要预判未来测试，也不要添加推测性功能。
- **一次一个切片。**每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于这个循环。**它属于审查阶段（见 `code-review` 技能），而不是红 → 绿实现循环。
