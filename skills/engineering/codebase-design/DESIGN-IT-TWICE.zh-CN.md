# 设计两次

当用户想为选定的深化候选项探索备选接口时，使用这种并行子代理模式。它源自 Ousterhout 的“Design It Twice”：你的第一个想法很可能不是最好的。

使用 [SKILL.md](SKILL.zh-CN.md) 中的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**、**杠杆效应（leverage）**。

## 流程

### 1. 界定问题空间

在生成子代理之前，为选定候选项编写一份面向用户的问题空间说明：

- 任何新接口都必须满足的约束
- 它将依赖什么，以及这些依赖属于哪一类（参见 [DEEPENING.zh-CN.md](DEEPENING.zh-CN.md)）
- 用于落实约束的粗略示意代码草图；它不是提案，只是让约束变得具体

向用户展示这份说明，然后立即进入第 2 步。用户阅读和思考时，子代理并行工作。

### 2. 生成子代理

使用 Agent 工具并行生成至少 3 个子代理。每个子代理必须为深化后的模块产出一个**截然不同**的接口。

为每个子代理提供独立的技术简报（文件路径、耦合细节、[DEEPENING.zh-CN.md](DEEPENING.zh-CN.md) 中的依赖类别、接缝背后放什么）。简报独立于第 1 步中面向用户的问题空间说明。为每个代理分配不同的设计约束：

- Agent 1：“最小化 interface，最多争取 1–3 个入口。最大化每个入口的 leverage。”
- Agent 2：“最大化灵活性，支持多种用例和扩展。”
- Agent 3：“针对最常见的 caller 优化，让默认情况极其简单。”
- Agent 4（如适用）：“围绕 ports & adapters 设计跨 seam 依赖。”

简报中同时包含 [SKILL.md](SKILL.zh-CN.md) 词汇和 CONTEXT.md 词汇，使每个子代理都能用架构语言和项目领域语言一致地命名事物。

每个子代理输出：

1. 接口（类型、方法、参数，以及不变量、顺序和错误模式）
2. 展示调用方如何使用它的示例
3. 实现在接缝背后隐藏了什么
4. 依赖策略和适配器（参见 [DEEPENING.zh-CN.md](DEEPENING.zh-CN.md)）
5. 权衡：哪里杠杆效应强，哪里较弱

### 3. 展示并比较

依次展示设计，让用户逐一理解，然后用文字比较。对比它们的**深度**（接口处的杠杆效应）、**局部性**（变更集中在哪里）和**接缝位置**。

比较之后给出你自己的建议：你认为哪种设计最有力，以及原因。如果不同设计中的某些元素适合组合，提出一个混合方案。要有明确立场：用户需要的是有力判断，而不是一份菜单。
