# 代码库设计

设计**深层模块**：以小型接口承载大量行为，将其置于清晰的接缝处，并可通过该接口进行测试。凡是设计或重构代码，都应使用这套语言和原则。目标是为调用方提供杠杆效应，为维护者提供局部性，并让所有人都能方便地测试。

## 术语表

严格使用这些术语，不要替换成“组件”“服务”“API”或“边界”。统一语言正是这一切的意义所在。

**模块（Module）**：任何拥有接口和实现的事物。特意不限定规模，可以是函数、类、包，也可以是跨层切片。_避免使用_：单元、组件、服务。

**接口（Interface）**：调用方为了正确使用模块而必须知道的一切：类型签名，以及不变量、顺序约束、错误模式、所需配置和性能特征。_避免使用_：API、签名（过于狭窄，只指类型层面的表面）。

**实现（Implementation）**：模块内部的代码主体。它不同于**适配器（Adapter）**：一个对象可能是实现很大的小型适配器（Postgres repo），也可能是实现很小的大型适配器（内存 fake）。讨论接缝时使用“适配器”，其他情况使用“实现”。

**深度（Depth）**：接口所提供的杠杆效应，即调用方（或测试）每学习一单位接口，就能调用多少行为。当大量行为隐藏在小型接口之后时，模块是**深层的（deep）**；当接口几乎与实现一样复杂时，模块是**浅层的（shallow）**。

**接缝（Seam）** _（Michael Feathers）_：无需在某处编辑代码就能改变行为的位置；模块接口所在的*位置*。接缝放在哪里本身就是一个设计决策，与其背后放什么不同。_避免使用_：边界（与 DDD 的限界上下文含义重叠）。

**适配器（Adapter）**：在接缝处满足某个接口的具体对象。它描述的是*角色*（填补哪个位置），而非实质（内部是什么）。

**杠杆效应（Leverage）**：调用方从深度中获得的收益，即每学习一单位接口，就能获得更多能力。一份实现可以在 N 个调用点和 M 个测试中持续产生回报。

**局部性（Locality）**：维护者从深度中获得的收益，即变更、缺陷、知识和验证集中在一处，而不是散落在各个调用方中。修复一次，处处修复。

## 深层与浅层

**深层模块** = 小型接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅层模块** = 大型接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时，问自己：

- 能否减少方法数量？
- 能否简化参数？
- 能否把更多复杂性隐藏在内部？

## 原则

- **深度是接口的属性，而不是实现的属性。** 深层模块的内部仍可由小型、可 mock、可替换的部分组成，只是它们不属于接口。模块既可以有**内部接缝**（实现私有，供自身测试使用），也可以在接口处有**外部接缝**。
- **删除检验。** 设想删除这个模块。如果复杂性随之消失，它只是一个透传层；如果复杂性重新散落到 N 个调用方中，它就确实发挥了作用。
- **接口就是测试表面。** 调用方和测试跨越同一道接缝。如果你想越过接口深入测试，模块的形状很可能不对。
- **一个适配器意味着假想接缝，两个适配器意味着真实接缝。** 除非确实有东西会跨越接缝发生变化，否则不要引入接缝。

## 为可测试性而设计

优秀的接口让测试自然发生：

1. **接收依赖，不要创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **缩小表面积。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，以其**接口**为参照进行衡量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处，并满足该**接口**。
- **深度**为调用方带来**杠杆效应**，为维护者带来**局部性**。

## 被否决的表述

- **把深度定义为实现代码行数与接口代码行数之比**（Ousterhout）：这会奖励用冗余代码填充实现。我们使用“深度即杠杆效应”的定义。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的 public 方法**：过于狭窄。这里的接口包含调用方必须知道的每一个事实。
- **“边界”**：与 DDD 的限界上下文含义重叠。应使用**接缝**或**接口**。
