# 深化

如何根据依赖关系，安全地深化一组浅层模块。本文假定你已掌握 [SKILL.md](SKILL.zh-CN.md) 中的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**。

## 依赖分类

评估某个深化候选项时，对其依赖进行分类。依赖类别决定了如何跨越接缝测试深化后的模块。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。始终可以深化：合并这些模块，并直接通过新接口进行测试。不需要适配器。

### 2. 可本地替代（Local-substitutable）

拥有本地测试替代品的依赖（例如用 PGLite 替代 Postgres、使用内存文件系统）。如果替代品存在，就可以深化。测试套件运行替代品来测试深化后的模块。接缝位于内部，模块的外部接口不需要 port。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个 **port**（接口）。深层模块拥有逻辑，传输机制则以**适配器**形式注入。测试使用内存适配器，生产环境使用 HTTP/gRPC/queue 适配器。

建议表述：*“在接缝处定义 port，为生产环境实现 HTTP 适配器，为测试实现内存适配器。这样，即便逻辑跨网络部署，它仍集中在一个深层模块中。”*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的 port，测试则提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假想接缝，两个适配器意味着真实接缝。** 除非至少有两个合理的适配器（通常为生产 + 测试），否则不要引入 port。只有一个适配器的接缝只是间接层。
- **内部接缝与外部接缝。** 深层模块既可以有内部接缝（实现私有，供自身测试使用），也可以在接口处有外部接缝。不要仅仅因为测试使用了内部接缝，就通过接口将它暴露出去。

## 测试策略：替换，而非叠加

- 一旦存在针对深化模块接口的测试，浅层模块原有的单元测试就成了废物，应删除它们。
- 在深化模块的接口处编写新测试。**接口就是测试表面。**
- 测试通过接口断言可观察结果，而不是内部状态。
- 测试应能经受内部重构：它们描述行为，而不是实现。如果实现一变，测试就必须跟着变，说明测试越过了接口。
