# 诊断 Bug

这是一套处理困难 bug 的纪律。只有在明确说明理由时才能跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在），以清晰理解相关模块，并检查所触及区域中的 ADR。

## 阶段 1：建立反馈循环

**这就是本技能的核心。**其他一切都只是机械操作。如果你拥有针对该 bug 的**紧密**通过/失败信号，也就是能在_这个_ bug 上变红的信号，你就能找到原因；二分、假设检验和插桩都只是在利用它。如果没有这样的信号，再久地盯着代码也救不了你。

在这里投入远超其他阶段的精力。**要强硬。要有创造力。拒绝放弃。**

### 构建反馈循环的方法，大致按此顺序尝试

1. 在能触达该 bug 的任何接缝处编写**失败测试**，可以是单元测试、集成测试或 e2e 测试。
2. 针对正在运行的开发服务器使用 **Curl / HTTP 脚本**。
3. 使用固定输入调用 **CLI**，并将 stdout 与已知正确的快照进行 diff。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，并对 DOM、console 或 network 作断言。
5. **重放捕获的 trace。**将真实的网络请求、payload 或 event log 保存到磁盘，在隔离环境中通过代码路径重放。
6. **一次性 harness。**启动系统的最小子集（一个服务、mock 依赖），通过一次函数调用覆盖 bug 的代码路径。
7. **Property / fuzz 循环。**如果 bug 是“偶尔输出错误”，运行 1000 组随机输入并寻找失败模式。
8. **二分 harness。**如果 bug 出现在两个已知状态（commit、dataset、version）之间，将“在状态 X 启动、检查、重复”自动化，以便运行 `git bisect run`。
9. **差异循环。**让同一输入分别通过旧版本与新版本（或两种配置），然后对输出做 diff。
10. **HITL bash 脚本。**最后手段。如果必须由人类点击，使用 `scripts/hitl-loop.template.sh` 驱动_人类用户_，使循环仍然结构化。捕获的输出会反馈给你。

建立正确的反馈循环后，bug 就已经解决了 90%。

### 收紧循环

把循环当作产品。一旦有了_一个_循环，就继续**收紧**它：

- 能否让它更快？（缓存 setup、跳过无关 init、缩小测试范围。）
- 能否让信号更精确？（对具体症状作断言，而不是只检查“没有崩溃”。）
- 能否让它更确定？（固定时间、设置 RNG seed、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环只比没有稍好；一个耗时 2 秒且确定的循环才足够紧密，是调试的强大能力。

### 非确定性 Bug

目标不是得到一次干净的复现，而是获得**更高的复现率**。将触发器循环 100 次、并行运行、增加压力、缩窄时序窗口、注入 sleep。复现率 50% 的 flake 可以调试，1% 则不行；持续提高复现率，直到它可供调试。

### 确实无法建立循环时

停下来并明确说明。列出你尝试过的办法。向用户请求：(a) 访问能够复现问题的环境，(b) 一份捕获的产物（HAR 文件、log dump、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。没有循环时，**不要**继续提出假设。

### 完成判据：一个能变红的紧密循环

当循环足够**紧密**且**能够变红**时，阶段 1 才算完成：你可以指出**一个命令**，可以是脚本路径、测试调用或 curl；你已经**至少运行过一次**（粘贴调用方式及其输出），并且它满足：

- [ ] **能够变红**：它驱动真实的 bug 代码路径，并对**用户描述的确切症状**作断言，因此能在这个 bug 上变红，并在修复后变绿。不能只检查“运行时没有报错”，它必须能够_捕获这个具体 bug_。
- [ ] **确定**：每次运行的判定相同（对于 flaky bug，按上文固定为较高的复现率）。
- [ ] **快速**：以秒计，而不是分钟。
- [ ] **代理可运行**：你可以无人值守地运行；只有通过 `scripts/hitl-loop.template.sh` 才允许人类处于循环中。

如果在这个命令存在之前，你发现自己正在阅读代码以建立理论，**立刻停下。直接跳到假设正是本技能要防止的失败。**没有能变红的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行该循环。观察它变红，也就是 bug 出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是附近恰好发生的另一个失败。错误的 bug 会导向错误的修复。
- [ ] 多次运行都能复现失败（对于非确定性 bug，则达到足够高、可用于调试的复现率）。
- [ ] 已捕获确切症状（错误信息、错误输出或缓慢耗时），以便后续阶段验证修复确实解决了它。

### 最小化

循环变红后，将复现场景缩减到**仍会变红的最小场景**。每次只移除一项输入、调用方、配置、数据或步骤，并在每次移除后重新运行循环，只保留支撑失败所必需的内容。

这样做的原因：最小复现能缩小阶段 3 的假设空间（剩下的可疑活动部件更少），并在阶段 5 成为干净的回归测试。

当**每个剩余元素都是必要的**时才算完成，也就是移除任意一个元素都会让循环变绿。

在完成复现和最小化之前，不要继续。

## 阶段 3：提出假设

在测试任何假设前，先生成 **3 到 5 个按优先级排序的假设**。只生成一个假设会让你锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说明它会产生什么预测。

> 格式：“如果 <X> 是原因，那么 <changing Y> 会使 bug 消失，或 <changing Z> 会使它恶化。”

如果无法说明预测，这个假设就只是感觉；丢弃它或将它明确化。

**测试前先向用户展示排序后的列表。**用户通常掌握能立即重排假设的领域知识（例如“我们刚部署了与 #3 有关的改动”），或者知道哪些假设已经被排除。这是成本很低但非常省时的检查点。不要因此阻塞；如果用户暂时不在线，就按你的排序继续。

## 阶段 4：插桩

每个探针都必须对应阶段 3 的一项具体预测。**每次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先使用 **Debugger / REPL 检查**。一个 breakpoint 胜过十条 log。
2. 在能区分各假设的边界添加**有针对性的 log**。
3. 绝不“记录所有内容再 grep”。

为**每条 debug log 添加**唯一前缀，例如 `[DEBUG-a4f2]`。结束时只需 grep 一次即可清理。没有 tag 的 log 会残留；有 tag 的必须删除。

**性能分支。**对于性能回退，log 通常是错误工具。应先建立基线测量（timing harness、`performance.now()`、profiler、query plan），然后二分。先测量，再修复。

## 阶段 5：修复并添加回归测试

在修复前编写回归测试，但前提是存在**正确的接缝**。

正确的接缝应让测试按照调用点实际发生的方式覆盖**真实 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用方，但测试只有一个；单元测试无法复现触发 bug 的调用链），在那里添加回归测试只会制造虚假信心。

**如果不存在正确的接缝，这本身就是结论。**记录下来。代码库架构正在阻止你锁定这个 bug。将其标记给下一阶段。

如果存在正确的接缝：

1. 在该接缝处把最小复现转为失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始的、未最小化的场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理与复盘

宣布完成前必须做到：

- [ ] 原始复现不再出现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或者已记录缺少接缝）
- [ ] 所有 `[DEBUG-...]` 插桩均已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到明确标注为 debug 的位置）
- [ ] 在 commit / PR message 中说明最终被证实的假设，让下一位调试者能够借鉴

**然后追问：什么措施本可以防止这个 bug？**如果答案涉及架构改动（没有良好的测试接缝、调用方纠缠、隐藏耦合），将具体情况交接给 `/improve-codebase-architecture` 技能。应在修复完成后提出建议，而不是之前；此时你掌握的信息比开始时更多。
