# 问题分诊

让项目 Issue 跟踪器中的 issue 通过一个小型分诊角色状态机。

如果此仓库将外部 pull request 视为请求入口（见 Issue 跟踪器配置），分诊也涵盖它们：**PR 是附带代码的 issue**，使用相同角色、状态和状态机；下文会以“对于 PR”标出少数差异。根据跟踪器配置将单独的 `#42` 解析为 issue 或 PR。

分诊期间发布到 Issue 跟踪器的每条评论或 issue **必须**以下列免责声明开头：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.zh-CN.md](AGENT-BRIEF.zh-CN.md)：如何编写持久有效的代理简报
- [OUT-OF-SCOPE.zh-CN.md](OUT-OF-SCOPE.zh-CN.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug`：某些内容损坏
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：正在等待报告者提供更多信息
- `ready-for-agent`：规格完整，可交给 AFK 代理
- `ready-for-human`：需要人类实现
- `wontfix`：不会处理

对于 PR，同样的状态要结合其附带代码理解：`ready-for-agent` 表示已经附上简报，代理应接手 diff 的下一步；`ready-for-human` 表示已准备好由人类合并。

每个已分诊 issue 应恰好带有一个类别角色和一个状态角色。如果状态角色冲突，标记冲突并在进行其他操作前询问维护者。

这些是规范角色名，Issue 跟踪器中实际使用的 label 字符串可能不同。映射应该已经提供；如果没有，运行 `/setup-matt-pocock-skills`。

状态转换：无 label 的 issue 通常先进入 `needs-triage`，然后转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖状态；标记看起来异常的转换，并在继续前询问。

## 调用方式

维护者调用 `/triage` 并用自然语言描述需求。解释请求并采取行动。例如：

- “显示所有需要我关注的内容”
- “我们看看 #42”（issue 或 PR）
- “将 #42 移到 ready-for-agent”
- “有哪些内容已经可以让代理接手？”

## 显示需要关注的内容

查询 Issue 跟踪器并按最早优先的顺序展示三个 bucket：

1. **无 label**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **`needs-info`，且报告者在上次分诊记录后有新活动**：需要重新评估。

当 PR 在范围内时，将外部 PR 加入这些 bucket，并在每行标记 `[PR]` 或 `[issue]`。发现列表只展示_外部_ PR（跟踪器配置定义谁属于外部）；协作者正在进行的 PR 不是分诊工作。此过滤只适用于发现列表；无论作者是谁，明确点名的 PR 始终要分诊。

展示数量和每项的一行摘要。让维护者选择。

## 分诊指定的 Issue 或 PR

1. **收集上下文。**完整阅读 issue 或 PR（正文、评论、label、作者、日期；对于 PR 还要阅读 diff）。解析之前的分诊记录，避免重复询问已经解决的问题。使用项目领域术语表探索代码库，并遵守所触及区域中的 ADR。针对代码库运行两项检查：(a) **冗余**：按领域概念（而不只是请求原文）搜索所请求行为的现有实现，并报告搜索位置。如果找到，该 issue 属于已经实现的 `wontfix`（步骤 5）。(b) **先前拒绝**：读取 `.out-of-scope/*.md`，指出与当前请求相似的内容。

2. **提出建议。**向维护者说明你建议的类别和状态、理由，以及与请求相关的简短代码库摘要，包括它是否已经实现。等待指示。

3. **验证主张。**在任何深入追问前，先检查主张是否成立。对于 bug，按照报告者的步骤复现。对于 PR，确认 diff 确实做到了它声称的内容：checkout 该分支，运行相关测试或命令。报告结果：已确认（附代码路径）、失败或细节不足（这是强烈的 `needs-info` 信号）。经过确认的验证能形成强得多的代理简报。

4. **深入追问（如需要）。**如果请求需要补充细节，同时运行 `/grilling` 和 `/domain-modeling` 技能，一次追问一个问题来打磨请求；在决策落定时改进领域术语，并就地更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发布代理简报评论（[AGENT-BRIEF.zh-CN.md](AGENT-BRIEF.zh-CN.md)）。
   - `ready-for-human`：使用与代理简报相同的结构，但注明无法委派的原因（判断、外部访问、设计决策、手工测试）。
   - `needs-info`：发布分诊记录（见下方模板）。
   - `wontfix`：关闭 issue，评论内容取决于_原因_：
     - **已经实现**：代码库中已存在该改动。指出实现位置；**不要**写入 `.out-of-scope/`（该知识库用于_被拒绝_的请求，而不是已经构建的内容）。
     - **拒绝（bug）**：礼貌解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接该记录，然后关闭（[OUT-OF-SCOPE.zh-CN.md](OUT-OF-SCOPE.zh-CN.md)）。
   - `needs-triage`：应用该角色。如果已有部分进展，可以选择添加评论。

## 快速覆盖状态

如果维护者说“将 #42 移到 ready-for-agent”，信任他们并直接应用该角色。确认即将执行的操作（角色变更、评论、关闭），然后行动。跳过深入追问。如果在没有追问会话的情况下移到 `ready-for-agent`，询问他们是否希望编写代理简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- 已确认事项 1
- 已确认事项 2

**What we still need from you (@reporter):**

- 问题 1
- 问题 2
```

将深入追问期间解决的所有内容记录在 “established so far” 下，避免工作丢失。问题必须具体且可行动，不能只是“请提供更多信息”。

## 恢复先前会话

如果 issue 或 PR 中存在之前的分诊记录，读取它们，检查报告者是否回答了未决问题，并在继续前展示更新后的情况。不要重复询问已经解决的问题。
